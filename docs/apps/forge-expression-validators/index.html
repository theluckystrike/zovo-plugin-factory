Expression Validators & Conditions for Jira

Workflow validators and conditions for Jira Cloud, built on Jira expressions. Pick a rule from the template library, fill in a short form, and click "Test against issue" to see the result before you publish the workflow. Advanced admins can write their own Jira expression.

Built on Atlassian Forge. Rules are evaluated by Jira itself, so the app sends no data outside Atlassian.

Rule templates

Each template is available as a validator, which blocks the transition and shows an error message, and as a condition, which hides the transition.

Validators can show your own error message. If you leave it empty, a message is written for you from the settings (for example "Fill in these fields before this transition: Components, Story Points."). The generated message is written again each time you save the rule, so it follows changes to the settings. A message you typed yourself is kept as you wrote it.

How to use

  1. Edit a workflow of a company-managed or team-managed project.
  2. Select a transition and add a validator or a condition.
  3. Choose one of the rules above. They are listed under their template names.
  4. Fill in the form. Field boxes accept a field name or id (for example Story Points or customfield_10010) and suggest fields as you type.
  5. Optional. Enter an issue key and click "Test against issue".
  6. Click Add or Update, then publish the workflow.

Test against issue

The test runs the rule now, as you, against the issue as it is saved (POST /rest/api/3/expression/evaluate, with the rule settings passed as config). A real transition can give a different result, for these reasons.

  • Jira also applies the values entered on the transition screen.
  • Jira evaluates the rule as the user who makes the transition, with that user's permissions.
  • transition, workflow, originalIssue and groupOperator exist only during a real transition, so custom expressions that use them cannot be fully tested.

Good to know

Values and lists

Status, work type, priority, resolution, label and option values are compared exactly, and the comparison is case-sensitive (Done is not done). Run "Test against issue" to check.

Separate list values with commas or new lines. A value that contains a comma goes in double quotes, for example "Yes, approved", No. The form shows each value it read as a separate chip.

Fields

The "Select field" trigger takes only option-type custom fields: single select, radio buttons, multi-select, checkboxes and cascading select. For a cascading select, the first-level value is compared. Number, text, date and user fields are refused, because they have no option value to compare.

The field boxes list at most 2,000 fields on very large sites. The cap keeps every supported system field, then custom fields in name order. The box itself lists fields by name, with system and custom fields mixed. If a site has more, the form says so and names the last listed field. You can't pick fields after it, but fields a rule already uses are kept, so you can still edit and save that rule.

If the field list can't be loaded, the fields already saved in a rule are kept and the rule can be saved again. You can choose other fields only after a reload.

Linked and child issues

Symmetric link types such as Relates ("relates to" in both directions) are offered only as "either direction", because a link made from the other issue has the opposite direction. A rule saved earlier with one direction keeps it, and the picker labels it as such.

"Linked issues are done" fails for a link when Jira returns that link without its issue. We expect Jira to do this when the user who transitions can't view the linked issue, but this isn't confirmed on a live site yet. Sub-tasks and child issues that user can't see may be skipped. Jira's documentation doesn't say whether it leaves them out of the list, and if it does, "Sub-tasks or child issues are done" doesn't check them.

Jira caps how much data one expression may load. Rules that read many linked issues or child issues can hit this cap on very large issues, and Jira then treats the rule as failed.

Regular expressions

Jira runs the pattern with its own regular-expression engine, not your browser's. When you save, the form checks the syntax in the browser. It also refuses common constructs that the two engines read differently: [], [^], [ or && inside a class, an unescaped { that is not a repeat count, \u/\x without the full hex digits, group names with _, inline flags such as (?i), and Unicode classes such as \p{Lu}. For a case-insensitive letter, use a class such as [Aa].

A backslash before a letter is accepted only for \d \D \s \S \w \W \b \B \n \r \t \f, \u and \x with their hex digits, \c with a control letter and \k<name>. Any other letter is refused. That covers escapes that Java-style engines refuse, such as \y, and escapes they read differently from the browser, such as \A, \z and \Q…\E. We haven't confirmed which engine Jira uses, so this check is cautious. Use ^ and $ instead of \A and \z.

Other rare differences can remain. So run "Test against issue" after you change a pattern, and if Jira rejects it, the test shows Jira's error. "Matches" means the pattern is found anywhere in the text. Use ^ and $ to match the whole value.

Custom expressions

Custom expressions use the expression override that Atlassian documents for Forge workflow rules (expression in the saved configuration). If Jira ever ignores the override, the rule blocks the transition with a message that says so, and a custom condition hides it. It never silently lets transitions through.

Uninstalling and licenses

Jira evaluates the rules on Atlassian's cloud. If the app is uninstalled, Jira treats its rules as failed: validators block and conditions hide transitions. Remove the rules from your workflows before you uninstall.

When a paid license lapses, existing rules keep running because Jira evaluates them. But rules can't be added, edited or tested until the license is active again.
