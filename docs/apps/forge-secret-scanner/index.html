Secret & PII Scanner for Confluence and Jira

Find leaked credentials and personal data in Confluence pages and Jira issues before someone else does, or before an AI assistant starts quoting them. Everything runs on Atlassian's Forge platform. The app has no external endpoints and sends no data outside your Atlassian site.

When two detectors match the same text, the more specific one wins (a GitHub token after token = is reported once, as a GitHub token).

The full value is never stored

A finding keeps the detector, severity, field, line, a masked value and up to 24 characters of text before it, so you can see password: or Card . That text gets scrubbed too. Other matches, groups of 4+ digits and credential-like runs become … or •••. A credential-like run means 10+ token characters with a digit or mixed case, or 8+ with both a digit and a letter, such as Tr0ub4dor (Jira issue keys, ISO dates and camelCase or PascalCase key names ending in a keyword, such as adminPassword or SMTPPassword, stay readable).

Values after a credential keyword are replaced as well, and so are values after a glued one (adminPassword: x → adminPassword: …, JWTSecret: x → JWTSecret: …, PGPASSWORD=x → PGPASSWORD=…). With : or = after the keyword, everything up to the end of the line or the next , / ; / . is replaced, so multi-word passphrases are hidden whole (password: my dog rex, mail → password: …, mail). Without an operator, the next word goes only when it has a digit or a symbol (PIN 739 → PIN …, PIN 12 34 → PIN …).

A secret in a page title is masked in the stored title, and titles get the same keyword and credential-run filter. But the filter isn't a guarantee. An undetected credential made only of lower-case letters and written with no keyword (for example login admin / sunflower), or one after an all-lower-case run-together keyword (dbpassword: sunflower), can still remain in a stored context or title.

Finding ids are hashes of the location plus a keyed fingerprint of the value. The fingerprint is HMAC-SHA256 with a random 256-bit secret that the app creates once per installation and keeps in its own Forge storage. So two different secrets with the same mask (every password masks to ********) get different ids, and nobody can match an id to a value without that installation's secret.

How scanning works

Automatic scans run when a page or blog post is created or edited, and when an issue is created, edited, commented on or deleted. You can turn them off, or skip spaces and projects, in Settings.

An administrator can also scan one space (all current pages and blog posts) or one project (all issues) on demand. The scan runs in the background in steps of at most 10 requests, with 25 pages or 50 issues per request, 100 ms between requests and a 2-second pause between steps. You can cancel it. When it finishes, findings of content that no longer exists in that space or project are removed.

On HTTP 429 or 503 the app waits as long as Retry-After asks (seconds or HTTP date, or a 1, 2, 4 s backoff without it). Only waits of up to 10 seconds happen inline, with at most 3 retries. For a 429 with a longer wait, or when the retries run out, the scan step stops and gets re-queued after Retry-After, at least 60 seconds and at most 15 minutes later. Fifteen minutes is the Forge queue's longest delay, so if Retry-After asks for more, the next step is rate-limited again and waits again. A 503 that doesn't clear counts as an error, which means a 30-second pause, and the scan stops after 5 errors in a row.

Page and issue events retry too. When one hits HTTP 429 or 5xx, the handler returns a Forge InvocationError so the platform delivers the event again after at least 60 seconds (longer if Retry-After asks, at most 15 minutes). Forge retries an event at most 4 times. After that, the next edit or a manual scan picks up the change. The retry request follows Atlassian's product-event docs but hasn't been exercised on a live site yet (NOTES.md).

If the space-key lookup for an event fails for any other reason, the page is still scanned and stored under its previous space key (or space <id>). A failed lookup never deletes findings.

In Jira the app reads the summary, description, environment and up to 100 comments per issue.

Admin page

In Confluence it's under Settings → Secret & PII Scanner. In Jira, look under Settings → Apps → Secret & PII Scanner.

The Findings tab filters by severity, status (open / false positive / all), category (secrets / PII), detector and space or project key. It shows 25 rows per page, most severe first.

Marking a finding as a false positive hides it, and the same value in the same field of the same page or issue stays hidden on later rescans. A different value is a new finding, even if it masks the same way. When the finding disappears (the value is removed, or the content is cleaned or deleted), the mark goes with it, so pasting the value again shows it again. Reopen undoes a mark.

Export CSV opens a dialog with the CSV text to copy, since UI Kit has no file download. One export holds up to 1,000 rows, so use filters for more. Cells that start with =, +, -, @, tab or CR get a leading ' so spreadsheets don't run them as formulas.

The Scan tab starts or cancels a space or project scan and shows progress. Settings covers auto-scan on/off, which detectors run, and the spaces or projects to skip in auto-scan. Keys are compared ignoring case, and Jira keys are saved in upper case.

Who can open it

On every request the app checks, as you, that you're a Confluence administrator (for the Confluence page, GET /wiki/rest/api/user/current?expand=operations, operation administer on the application) or hold the Administer Jira global permission (for the Jira page, GET /rest/api/3/mypermissions?permissions=ADMINISTER). Anyone else gets "Only … administrators can use this page". If the check itself fails, the request is refused.

The first time you open the page, Atlassian may ask you to allow the app to act as you. These checks need that.

Findings in content you can't open

The app checks, as you, which of the stored pages or issues you can open. Findings in content you can't open (restricted or deleted) are left out of the list, the totals, the severity counts and the CSV export, and you can't change their status. A notice says that some findings were left out, without saying how many. If the check fails, no findings are shown.

Performance and ReDoS safety

All patterns use bounded repetition and look-behind anchors, so each run of characters is tried from its start only. test/redos.test.js runs every detector against 59 adversarial 1 MB inputs (repeated prefixes like AKIA, ghp_, eyJ, -----BEGIN …, password=, aPassword=, APASSWORD=, postgres://a:, ab://, comma-joined URL credentials, URL lists whose first URL is skipped, ABPassword=, nextPageToken: , BYPASS=, Bearer , mysql -u , card + expiry groups, digits, a@, very long local parts…) and checks that 4× more input takes well under 16× the time.

On the build machine (2026-11-05, after fix round 4) the slowest detector/input pair took 64 ms per 1 MB (url-credentials on repeated ab://). The full detector stays under about 0.25 s per 2 MB field. The tests allow 1.5 s per pair so they don't flake on slow CI.

Privacy and security

See PRIVACY.md. Scopes are read:confluence-content.summary (needed by the Confluence content events), read:page:confluence, read:blogpost:confluence, read:space:confluence, read:confluence-user (the Confluence administrator check), read:jira-work and storage:app. There are no write scopes on Confluence or Jira, and storage:app writes only to the app's own storage. No external fetch, no remotes.

Known limitations

What isn't scanned

  • Attachments, page versions/history, inline comments, Confluence footer comments, whiteboards and databases. In Jira, custom fields and attachments.
  • Content the app itself can't see, for example pages restricted so the app user has no access.
  • Excluded spaces and projects, but only in automatic scans. If a Confluence event doesn't name the space, the app looks the space key up from the page's space id before it decides. A manual scan of an excluded space still runs.

Detection limits

  • Detection is pattern-based. It'll miss secrets with no recognisable shape or keyword, and it can flag look-alike strings. Mark those as false positives.
  • A card number followed directly by another 4-digit group is reported only when that group looks like an expiry and the text says so (a CVV after it, or a card keyword before the number). Otherwise it's treated as part of a longer reference number. So ref 4539 1488 0343 6467 0927 and ref 4539 1488 0343 6467 2031 7765 aren't reported, while Visa 4539 1488 0343 6467 0927 and 4539148803436467 0927 123 are.
  • Keywords glued to the word before them are recognised only at a case change, as in camelCase (dbPassword, slackToken), PascalCase after an acronym (DBPassword, AWSSecretKey, JWTSecret) or upper case (PGPASSWORD, REDISPASS). All-lower-case run-together names (dbpassword=…, slacktoken=…) aren't detected, because they can't be told apart from ordinary words that contain pass or token. A glued Pass/PASS counts only right before the operator (dbPass=, REDISPASS=), only with a value that has a digit or a symbol (so REDISPASS=sunflowerTwo isn't reported, but db_pass=sunflowerTwo is), and never as the end of compass, bypass, surpass, trespass, overpass or underpass. That keeps COMPASS=NorthWest, BYPASS=CacheLayer2 and onPass: handleSuccess from being read as passwords.
  • A token keyword right after next, page, skip, continuation, sync, cursor, resume or max (NextToken, nextPageToken, skipToken, continuationToken, next_page_token) is treated as a pagination cursor and not reported, even if someone stores a real credential under such a name. idToken and refresh_token are still reported.
  • Some things are left out on purpose, to stay precise. Unquoted multi-word passwords (password: correct horse battery staple) aren't detected, though the stored context hides them. Neither are Basic credentials shorter than 16 base64 characters or lower-case IBANs.
