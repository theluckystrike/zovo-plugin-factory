7. How to run the sprint

Do these steps in the wave 18 folder (run-20261107/wave18). Do the steps in sequence.

A. Start a lane

  1. Write the brief in briefs/<LANE>.md. Give the seat in the first line, for example "(seat zovo-team2)".
  2. In the wave 18 folder, run zsh launch.sh <LANE> <seat> <timeout in seconds>.
  3. launch.sh waits until the disk and the memory have sufficient free space. Builders need 20 GB, verifiers need 15 GB, and other lanes need 8 or 12 GB. All lanes need 25% free memory.
  4. launch.sh opens the tmux session w18-<LANE>. It writes the log in logs/<LANE>.log and a START line in driver.log.
  5. launch.sh does not start a lane that has out/<LANE>.done or an open session.

B. Schedule lanes (sched25.sh)

  1. sched25.sh runs in the tmux session w18-SCHED24. Each 2 minutes it starts the lanes that are due. It stops at END24 (18 Nov 01:00).
  2. To add a lane, add one line go <LANE> <seat> <seconds> with its time condition.
  3. Do not edit sched25.sh while it runs. Copy it to a new file, edit the copy, stop the session w18-SCHED24, and start the copy in a new session w18-SCHED24.
  4. sched25.sh starts a codex lane again each 6 minutes while the seat has a usage limit. This is not an error.

C. Read the publish queue (cand5.py)

  1. Run python3 -I out/PUB5-scripts/cand5.py. Each row starts with OK, WAIT or HOLD.
  2. OK means that the build has all PASS verdicts. The publish job takes OK rows only.
  3. WAIT means that a PASS is missing. The row gives the verifier groups that must give a PASS.
  4. HOLD means a BLOCK, a supersede note, or a vsix file that is missing or changed.
  5. The LANES table in cand5.py gives the group of each builder lane. The job ignores a lane that is not in LANES.
  6. The UPD table gives the verifier groups for updates. The NEWRULE table gives the verifier groups for new listings.
  7. Before the first READY row of a new builder lane, add the lane to LANES and to UPD or NEWRULE. Make a backup (.bak-<lane>) first.

D. Keep the publish job running (pub6restart.sh)

  1. The publish job is pub5.sh in run6.sh, in the tmux session w18-PUB6R. At 2026-11-17 09:11, the job is running.
  2. The last publish start is at CUT (16 Nov 08:00). The job stops at END (16 Nov 08:30).
  3. To see if the job runs, run pgrep -fl pub5.sh.
  4. If the job stopped, run tmux new-session -d -s w18-PUB6R "zsh pub6restart.sh". pub6restart.sh waits until no job runs. Then it starts run6.sh with CUT 16 Nov 08:00 and END 16 Nov 08:30.
  5. Do not start a second job. pub5.sh holds a lock in out/PUB6-data/lock.d. A second job stops with exit code 3.
  6. Read out/PUB6-data/publish.out for the reason of each WAIT or HOLD.

E. Control the build slots (slotguard.sh)

  1. slotguard.sh runs in the tmux session w18-SLOTGUARD. Each 30 seconds it writes the cap in /tmp/buildslots/slots.max.
  2. The cap is 6 when the memory has 35% free or more and the disk has 20 GB free or more. In other conditions, the cap is 2.
  3. Start each heavy build with ~/bin/buildslot <command>. Do not change the cap manually.
  4. At END24, slotguard.sh sets the cap to 2 again.

F. Keep the disk free (diskfix.sh)

  1. diskfix.sh runs in the tmux session w18-DISKFIX. Each 10 minutes it reads the free disk space.
  2. When the disk has less than 20 GB free, it removes temporary caches with the guarded delete script. The script writes each deletion in a manifest.
  3. When the disk has less than 10 GB free, it writes an ALERT line in driver.log. Then stop and tell the owner.

G. Continue a lane (resume note)

  1. relaunch4.sh runs in the tmux session w18-RELAUNCH. Each 2 minutes it looks for a lane log with an EXIT= line and no out/<LANE>.done.
  2. It adds a RESUME NOTE to the end of the brief. It moves the old log to logs/<LANE>.log.1. Then it starts the lane again.
  3. It writes out/<LANE>.relaunched. It starts a lane again only one time.
  4. A resumed agent must read its own out/<LANE>* files first. It must not do finished steps again. It must write out/<LANE>.done at the end.
  5. If you continue a lane manually, use the same note. Add "RESUME NOTE (HH:MM): the first run ended without out/<LANE>.done. Read your own out/<LANE>* files and continue from there; do not redo finished steps; write out/<LANE>.done at the end." to the brief. Then run launch.sh.

H. Do these steps on a 5-hour limit

  1. Look for "hit your 5-hour limit" or "hit your usage limit" in logs/<LANE>.log. The line gives the reset time.
  2. relaunch4.sh moves the lane to the next seat in the order zovo-team2, zovo-team3, zovo-team4, zovo-team5. It uses only a seat with no limit message in the last hour.
  3. If all seats have a limit, wait until the reset time. Then start the lane with launch.sh on its brief seat.
  4. Do not start a lane on a seat that has a limit. The session stops immediately.
  5. Write each seat change in driver.log, for example "ORCH 5h limits: <LANE> relaunched <seat>".

I. Do these steps on a BLOCK

  1. A verifier writes BLOCK and the reason in out/VER-verdict.tsv for the exact sha256.
  2. cand5.py then shows the build as HOLD. The publish job does not publish it.
  3. The builder lane or FIXV3 repairs the cause. It increases the patch number, makes one build and writes a new READY row.
  4. Do not change or remove the BLOCK row. Each new sha256 needs new verdicts from two verifiers.
  5. If the BLOCK is incorrect, the verifier writes a new row for the same sha256. The last row of each verifier is the valid verdict.

J. Do these steps when the disk has less than 20 GB free

  1. Do not start a build, a test suite or a browser.
  2. Run coldstore --json plan --rules ~/.config/coldstore/rules-7d.conf.
  3. If the plan shows candidates, run coldstore push --from-plan --rules ~/.config/coldstore/rules-7d.conf --batch-mb 512 --yes --delete-local. Do not push items one at a time.
  4. Let diskfix.sh remove the caches. buildslot holds new builds until the disk has 25 GB free.
  5. When the disk has less than 10 GB free, stop. Tell the owner. Do not delete data to continue.

K. Finish a lane

  1. Write out/<LANE>.md. Give what you did, the evidence, the numbers (F for fetched, E for estimate), the open items and the owner steps.
  2. Write out/<LANE>-deletions.txt with the size and the path of each deletion.
  3. Write out/<LANE>.done with one line. Start the line with the lane name and the time.
