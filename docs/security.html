Security policy for Zovo Atlassian apps

Last updated: 18 November 2026. This policy applies to the Zovo apps on the Atlassian Marketplace. The publisher is the company, vendor name Zovo.

1. Report a security issue

  • Send the report to support@zovo.one. Put "Security" in the subject line.
  • Tell us the app name, the steps to reproduce the issue and what an attacker can do with it.
  • Do not put customer data or secrets in a public GitHub issue.
  • We reply within 1 business day. Our business hours are Monday to Friday, 09:00 to 17:00 UTC+7.
  • We tell you when we accept the issue, when the fix is released, and if we need more information.

2. Security incident handling

A security incident is an event where customer data can be read, changed or lost by a person who must not have access, or where an app does not work as designed because of an attack. When we find or get a report of an incident, we do these steps:

  1. Notify Atlassian. We open a P1 ticket with Atlassian Marketplace within 24 hours. While the incident is open, we send an update at least every 6 hours.
  2. Contain. We stop the cause as fast as possible. We can disable a function, deploy a fix or ask Atlassian to hide the app.
  3. Investigate. We find the root cause, the time period, the affected sites and the data that was involved.
  4. Fix. We remove the root cause and add a test so that the same problem does not come back.
  5. Notify customers. We tell the affected customers within 72 hours after we identify the incident, where we can identify them. We use the Atlassian incident communication template.
  6. Review. We do a post-incident review and send the results to Atlassian in the incident ticket.

These steps follow the Atlassian security incident guidelines for Marketplace partners.

3. Vulnerability management

  • Sources. We get vulnerability reports from , from Atlassian Marketplace Security tickets and from dependency scans.
  • Triage. We confirm the issue and give it a severity with CVSS.
  • Fix time. We fix each issue within the time limits of the Atlassian security bug fix policy:
    SeverityCVSS scoreFix released within
    Critical9.0 to 10.010 days
    High7.0 to 8.94 weeks
    Medium4.0 to 6.912 weeks
    Low0.1 to 3.925 weeks
  • Release. We fix the code, run the app's unit tests, run npm audit and deploy the new version with the Forge CLI. Forge apps update on customer sites without action from the customer.
  • Dependencies. We run npm audit before each release. When a library has a known vulnerability, we update it or pin a fixed version.
  • Notification. For a critical vulnerability, we tell Atlassian and the affected customers. We use the Atlassian vulnerability notification template.

4. Security controls

Hosting

  • All Zovo Atlassian apps are Forge apps. Their code runs on Atlassian's Forge platform, and their data stays in Forge storage (Forge key-value storage or Forge SQL) on Atlassian.
  • Zovo runs no servers for these apps. The apps do not use Forge Remote or web triggers.
  • No data leaves the Atlassian cloud, unless the app's privacy notice says so. One app sends requests outside Atlassian: Code Snippets from GitHub Gists reads gists from api.github.com. It sends only read (GET) requests and stores nothing on GitHub.

Access control and authentication

  • Users sign in with their Atlassian account. The apps do not ask for Atlassian passwords or API tokens.
  • Each app asks only for the Forge scopes that its functions need. The scopes are in the app's manifest and on its Marketplace listing.
  • Product API calls run as the current user (asUser), so a user sees only the content that Jira or Confluence permissions let that user see. Four apps also make calls as the app (asApp) for background jobs, for example scheduled scans and reminders. Each app's documentation tells what these jobs do.
  • Only Zovo staff can deploy the apps. The source code account requires two-factor authentication.

Data protection

  • Atlassian encrypts the traffic between users, the Forge platform and the Atlassian product APIs with TLS.
  • Atlassian encrypts Forge hosted storage at rest.
  • Zovo keeps no copies of customer data outside Atlassian.
  • The Gists app can store an optional GitHub token that a site admin enters. The app keeps it in Forge secret storage and does not write it to logs.

Secure development

  • The apps check user input in the backend functions before use. REST paths are checked against an allow-list of endpoints. Forge SQL queries use bound parameters. User text is shown as text. Where an app shows Markdown as HTML, it sanitizes the HTML first.
  • Each app has unit tests, including tests for input checks, escaping and permission checks. The tests run before each release.
  • The development computer uses full disk encryption, automatic operating system security updates and malware protection.

Logging and monitoring

  • The apps write logs to the Forge platform. Forge adds a time stamp to each log line.
  • The logs contain error names, status codes and counts. They do not contain passwords, tokens or the content of pages and issues.
  • Only the app developer can read the Forge logs in the Atlassian developer console.

5. What we do not claim

  • the company does not hold ISO 27001, SOC 2, PCI DSS or HIPAA certification.
  • We do not take part in the Marketplace bug bounty program at this time, and we have not done a third-party penetration test.

Privacy notices for each app are linked from the Atlassian apps page. Questions about this policy: support@zovo.one.
